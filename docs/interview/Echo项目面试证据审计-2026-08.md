## 一、执行摘要

Echo 适合作为 AI 应用岗位的主面试项目，但目前最需要解决的问题不是继续增加功能，而是把已经存在的产品判断和工程实现转化为可复现、可量化、可解释的证据。

项目已经具备一个较完整的真实产品闭环：从 LLM 页面捕获高价值想法，在浏览器侧边栏中本地保存、搜索、管理，并根据当前选择内容尝试召回历史 Echo。项目经历过一次明确的方向推翻，也经历过召回误匹配、Chrome MV3 写入竞态、动态页面定位失败等真实问题。这些经历能够证明产品判断、端到端实现、故障诊断和迭代能力。

当前主要缺口是：召回效果尚未在真实标注集上量化；向量实验仍是小规模合成数据；缺少统一的延迟、失败、成本和行为反馈记录；没有真实外部用户或云端生产流量；项目经历与技术取舍还没有整理成面试官容易验证的 Case Study。

因此，Echo 当前可以被定义为：

> 一个已经可运行、经过持续 dogfood、具有真实可靠性处理和实验意识，但评测体系与生产证据仍需补强的本地优先 AI 记忆与上下文召回产品。

如果未来几天完成真实 Recall Benchmark、BM25/Vector/Hybrid 对照、轻量 Trace 报告和面试 Case Study，项目足以成为 AI Product Engineer、AI 全栈应用工程师和 LLM Application Engineer 岗位的核心作品。它不适合被包装成大规模后端系统、模型训练项目或成熟商业化产品。

## 二、项目定位

### 2.1 用户问题

用户在 ChatGPT、Claude、Gemini、Grok 等 LLM 中会产生大量有价值的判断、灵感和阶段性结论，但这些内容通常被埋在长对话和不同平台中。传统收藏只解决“存下来”，没有解决“未来在合适语境中重新出现”。

Echo 的目标是：

1. 在用户产生想法时，以尽可能低的摩擦捕获；
2. 保存原始上下文、用户想法和来源锚点；
3. 在未来相似语境中安静地召回相关 Echo；
4. 保持本地优先、可解释和人在回路，不自动替用户做决定。

推荐用于简历和面试的项目描述：

> Echo 是一个面向重度 AI 使用者的本地优先记忆与上下文召回系统。它从多个 LLM 网页中捕获高价值想法，利用可解释的词法与语义召回实验，在未来工作语境中重新呈现相关内容，并通过严格的拒绝策略降低误打扰。

## 三、目前已经具备的关键证据

### 3.1 可运行的端到端产品

Echo 不是静态原型，而是基于 Chrome Manifest V3 和 Plasmo 的可运行浏览器扩展，主技术栈包括 React、TypeScript、Tailwind、Dexie 和 IndexedDB。

已经实现的主要工作流包括：

- 在 ChatGPT、Claude、Gemini、Grok/X 页面中捕获选区；
- 区分外部触发文本、用户想法和推断内容；
- 本地保存、搜索、复制、固定、删除、撤销和备份；
- 从 Echo 返回原始对话位置；
- 根据当前页面选区触发 Reflection Probe；
- 展示匹配原因和完整诊断报告；
- 在不满足阈值时保持沉默。

这一部分能够证明：候选人可以从用户问题出发，完成浏览器环境中的交互、数据持久化、跨页面通信和完整产品闭环。

### 3.2 真实的产品方向推翻

项目最初更接近独立的 Collect 工具，但 dogfood 发现用户不愿意为了找回内容主动打开本地应用。“保存后去另一个地方管理”的路径无法形成自然使用闭环。

项目随后转向 Echo：把捕获和浮现放进用户本来就在使用的浏览器与 LLM 页面中，并把目标从“收集更多内容”收缩为“在合适的时机还回一个有价值的旧想法”。

这段经历的重要性在于：

- 推翻的原因来自真实使用摩擦，而不是追逐技术趋势；
- 转向改变了产品入口、交互方式和核心价值，不只是视觉调整；
- 项目保留了旧实现作为历史边界，能够还原决策过程；
- 后续技术方向围绕“低打扰、高精度、可解释”展开，与新产品目标一致。

这是面试中最值得讲的产品工程故事之一。

### 3.3 基于真实诊断数据改造召回算法

第一版 Reflection Probe 使用中文字符片段和词法累加，dogfood 后出现明显误匹配：`实用`、`这个`、`快速` 等泛词也能产生看似很高的相关性。

项目没有直接增加模型或继续凭感觉调权重，而是先加入：

- 每个候选的完整评分 ledger；
- 接受与拒绝原因；
- 字段贡献、词频、IDF、BM25 子分数；
- 可复制的 Probe Markdown 报告；
- selection、intent 和 match kind 的诊断分类。

随后审计了 16 份 Probe 报告、1,493 次候选扫描和 256 个被接受候选，发现：

- 平均每个选区接受 16 个候选，明显不符合“安静浮现”的目标；
- 139 个接受结果只匹配一个词；
- 250/256 没有连续短语证据；
- 252/256 的最强字段来自原始触发文本；
- 76 个结果仅凭单词就得到 60 分以上。

基于这些数据，系统改成 precision-first lexical gate：单词匹配不再浮现；双词只进入诊断；需要连续短语或至少三个有效词才可展示；高频词降级；重复结果被抑制。

这部分已经能够证明：

- 能将模糊的“召回不准”转化为可诊断问题；
- 能使用数据推翻原算法；
- 理解 precision、recall 与用户打扰成本之间的产品权衡；
- 不把未经校准的分数错误描述为置信度。

### 3.4 动态网页中的可靠锚点

LLM 网页会发生 DOM 变化、消息虚拟化、历史内容卸载和平台结构变化。Echo 的 Anchor v2 使用多层定位策略：

1. 唯一的 provider 原生消息 ID；
2. 规范化全文的 SHA-256 指纹；
3. 首尾指纹与长度漂移容忍；
4. 前后消息指纹消歧；
5. 容器文本、前缀、后缀和相似度回退；
6. 对虚拟化历史进行有限次数的滚动与重试；
7. 无法可靠定位时返回失败，不强行跳到低置信候选。

这是比普通网页剪藏更扎实的工程证据，可以用于回答“第三方页面变化如何处理”“如何设计降级路径”“怎样避免错误定位”等问题。

### 3.5 Chrome MV3 竞态与恢复机制

dogfood 中曾出现 Collect 后补充想法时保存失败。根因与 Chrome MV3 Service Worker 生命周期及 Dexie 更新竞态有关。

处理方式包括：

- 写入前读取记录；
- `update` 失败后使用完整记录 `put`；
- 先把待写想法放入 `chrome.storage.local` 队列；
- Dexie 成功后清除队列；
- Service Worker 暂时不可用时，由已打开的 Side Panel 在刷新阶段重新应用；
- extension context 失效时向用户提供可执行的恢复提示。

这可以作为“失败恢复、最终一致性和浏览器运行时约束”的真实案例。它不能等同于分布式队列系统，但比单纯展示成功路径更有面试价值。

### 3.6 自动化测试与构建纪律

2026-08-03 的本地验证结果：

- 9 个测试文件通过；
- 51 个测试通过；
- 测试运行时间约 1.17 秒。

测试覆盖包括捕获区域识别、消息指纹、备份、Pin 状态、意图分类、卡片展示、相关性排序、搜索和 Probe 报告。

现有开发日志还保存了各阶段 TypeScript 检查、构建和回归测试记录。当前报告只把本次实际运行的 51 个测试作为最新可验证结果，不把历史测试数量与当前状态混用。

### 3.7 向量召回实验与正确的实验边界

项目已经建立 BM25 与向量检索对照实验：

- BM25 侧直接复用产品中的真实 `analyzeRelatedEchoes`，不是近似重写；
- 向量侧使用本地 `multilingual-e5-small` embedding 和 TiDB 向量距离；
- 两侧使用相同字段；
- 实验代码与产品扩展隔离，没有未经验证就接入正式工作流。

现有合成实验包含 18 条 Echo、6 个查询和 Top-5 对照结果：

- 向量把相关 Echo 放入 Top-3 的查询为 6/6；
- 词法为 2/6；
- 向量 Top-3 平均精度为 33%；
- 词法为 25%；
- 向量 Top-5 相似度普遍拥挤，固定阈值无法可靠区分相关与无关。

正确结论不是“向量方案已经胜出”，而是：向量能补足换词表达下的召回，但裸 embedding + cosine 不符合 Echo 的低打扰要求，后续应验证 hybrid candidate generation、rerank 或更严格的拒绝机制。

## 四、目前缺失的关键性证据

### 4.1 缺少真实标注的离线评测集（最高优先级）

现有 1,493 次扫描来自真实 Probe 诊断，但主要用于发现旧算法的误接受模式，没有形成稳定的 query-to-relevance 标注集。向量实验则只有 18 条合成 Echo 和 6 个查询，样本太小，也不是真实个人数据。

因此目前不能严谨回答：

- 当前 BM25 的 Precision@3 和 Recall@3 是多少；
- Hybrid 是否真的优于纯词法或纯向量；
- 系统每 100 次上下文会产生多少次误打扰；
- 系统选择沉默时，有多少次错过了真正有用的 Echo；
- 不同类型查询在哪种召回策略下表现更好。

这是当前最关键的证据缺口。没有 benchmark，embedding、reranker、阈值和模型选择都只能算实验想法，不能算经过验证的 AI 工程能力。

### 4.2 缺少统一的线上/本地可观测性

当前 Probe Debug Panel 已经能够解释候选分数和拒绝原因，但还没有形成统一的请求级 trace，缺少：

- 每次召回的 trace ID；
- 分词、候选生成、去重、排序、展示的阶段耗时；
- 候选数量与拒绝原因分布；
- 捕获、定位、召回和存储失败率；
- 回退路径是否被触发；
- 可导出的汇总报告。

因为产品是 local-first，不必为了“生产级”强行接入一套云监控。更合理的证据是提供本地、可选择导出、默认不上传的结构化 Trace Report，并说明隐私边界。

### 4.3 缺少用户反馈闭环

目前系统知道“算法认为相关”，但不知道用户是否真的觉得有用。尚未系统记录：

- 展开；
- 复制；
- 返回来源；
- 不相关；
- 内容相关但现在不想看；
- 想法已经改变；
- 永不再浮现。

其中必须区分“内容不相关”和“时机不对”。否则系统会把一条长期有价值、只是当前不合时宜的 Echo 错误地当成无效内容。

面试层面至少需要一个最小反馈数据模型和本地事件记录，才能说明如何从离线评测过渡到真实使用反馈。

### 4.4 缺少延迟、资源和成本证据

当前不能准确回答：

- 100、1,000、10,000 条 Echo 下的搜索和召回延迟；
- embedding 首次加载时间与缓存后延迟；
- IndexedDB 读取、分词、BM25、向量和 rerank 各自耗时；
- 浏览器扩展的内存占用；
- 如果增加 LLM 生成层，单次请求成本和失败重试成本是多少。

这部分不需要大规模压测，但需要至少提供几个固定数据规模下的可重复 benchmark，并区分冷启动与热运行。

### 4.5 缺少正式的 Hybrid Recall 结果

目前已经验证了“纯词法容易漏掉换词表达”“纯向量容易产生相似度拥挤”，但尚未实现并评测：

```text
lexical candidates ∪ semantic candidates
→ deduplicate
→ precision-first rerank
→ abstain / surface
```

因此“Hybrid 会更好”目前仍是假设。需要通过同一个真实 benchmark 与 BM25、Vector 做对照，才能成为证据。

### 4.6 缺少安全与隐私威胁模型

项目有清晰的本地优先原则，但还缺少简短、系统化的威胁模型，例如：

- 扩展可以读取哪些页面内容；
- 临时 selection 是否持久化；
- IndexedDB 中保存哪些敏感字段；
- 导出文件可能包含什么隐私数据；
- 第三方 embedding 或 LLM 接入时，哪些数据会离开设备；
- Prompt injection、恶意网页 DOM 和来源伪造如何处理；
- 用户如何删除和迁移数据。

目标 AI 岗位经常会询问数据边界和模型调用风险，这份文档能低成本提高项目完整度。

### 4.7 缺少外部用户与生产环境证据

当前主要证据来自个人 dogfood。尚无可靠数据证明：

- 有多少真实用户长期使用；
- 7 日或 30 日留存；
- 每周捕获与召回次数；
- 用户是否因 Echo 改变工作结果；
- 不同用户的数据分布和容忍度差异。

这一缺口不能在几天内通过包装解决，也不应该虚构。面试时应明确说明当前处于个人 dogfood / alpha 阶段，并把已有证据描述为“准生产级工程验证”，而不是“大规模生产验证”。

### 4.8 缺少后端、鉴权和部署证据

Echo 当前是浏览器内、本地优先、无服务端产品，因此不能证明多租户鉴权、云数据库、任务队列、服务部署、限流、SLA 和线上回滚能力。

这对 AI Product Engineer 不是致命问题，但会限制它对纯全栈后端岗位的说服力。几天内不建议为了填简历临时搭建没有真实必要的后端。更好的做法是清楚解释：为什么当前版本选择 local-first，以及未来哪些能力（加密同步、跨设备、团队空间）才真正需要服务端。

## 六、未来几天的最小补强计划

### P0：真实 Recall Benchmark

建议产物：`evals/recall-benchmark/`

最小范围：

- 从真实 Echo 中脱敏导出 100～300 条记录；
- 整理 30～50 个真实或高度贴近真实的 selection/query；
- 每个查询标注 0～3 个应召回 Echo；
- 加入困难负例、过期想法、中英混合、长文本和同词异义；
- 固定数据版本、随机种子、算法配置和结果报告。

最低指标：

- Precision@3；
- Recall@3；
- MRR 或第一个相关结果排名；
- 每 100 次查询的误浮现次数；
- Abstention accuracy（保持沉默是否正确）；
- 按 query 类型拆分的结果。

完成标准：任何人执行一条命令都能从固定数据生成相同报告；报告同时包含总体指标和代表性失败案例。

### P0：BM25 / Vector / Hybrid 对照

在同一 benchmark 上比较三种方案：

1. 当前产品 BM25 + precision gate；
2. embedding + cosine；
3. lexical 与 semantic 候选合并后的 Hybrid + rerank / rejection。

必须记录：

- 使用的 embedding 模型与版本；
- 阈值和参数来源；
- 冷启动与热运行延迟；
- 每种方案的指标；
- 各自最常见的失败类型；
- 是否达到上线门槛。

最有价值的结果不一定是 Hybrid 获胜。若实验显示语义召回带来的误打扰超过收益，决定暂不上线同样是强证据，前提是判断来自可复现数据。

### P1：本地 Recall Trace

建议为每次分析生成类似结构：

```json
{
  "traceId": "...",
  "queryLength": 84,
  "corpusSize": 250,
  "stages": {
    "loadMs": 8,
    "tokenizeMs": 3,
    "lexicalMs": 12,
    "semanticMs": 47,
    "rerankMs": 5
  },
  "candidates": 24,
  "accepted": 2,
  "rejections": {
    "weakEvidence": 12,
    "duplicate": 3,
    "belowThreshold": 7
  },
  "fallbacks": [],
  "totalMs": 75
}
```

默认只保存在本地调试环境，由用户主动导出，不自动上传。面试演示时可以从一次选择直接展示结果、解释和 trace。

### P1：最小反馈事件

至少定义并实现：

- `shown`；
- `expanded`；
- `copied`；
- `opened_source`；
- `not_relevant`；
- `wrong_time`；
- `idea_changed`。

短期不必训练个人化模型，但应该能说明这些信号未来如何用于阈值、冷却和排序校准。

### P1：面试 Case Study

建议单独形成一份 2～4 页的项目案例，结构固定为：

1. Problem：AI 对话中的高价值想法无法自然回到未来工作流；
2. Initial hypothesis：用户会主动打开独立工具管理收藏；
3. Failure：dogfood 证明入口摩擦破坏使用闭环；
4. Pivot：转为浏览器内 local-first 记忆层；
5. Technical challenges：动态 DOM 锚点、MV3 生命周期、召回误打扰；
6. Evaluation：真实 benchmark 和三种召回策略对照；
7. Results：指标、延迟、失败案例和最终上线判断；
8. Trade-offs：为什么保持安静、为什么不直接上向量、为什么暂时无后端；
9. Next steps：反馈学习、记忆冲突治理和可选加密同步。

### P2：安全与隐私说明

补一页 threat model 和 data flow 即可。它的优先级低于 benchmark，但成本不高，能显著提高完整度。

## 七、建议暂时不要做的事情

未来几天不建议投入：

- 为了显得“全栈”临时增加无实际用途的登录和云数据库；
- 把所有本地 Echo 上传给第三方 LLM；
- 做复杂多 Agent 编排；
- 自研向量数据库或模型；
- 同时增加 PDF、图片、网页、文件夹等多种摄入源；
- 用大量生成式摘要掩盖召回质量不足；
- 在没有 benchmark 前反复调整阈值；
- 把合成数据实验描述为真实用户结果。

这些工作会增加功能数量，却不一定增加面试官可以验证的能力证据。

## 八、面试叙事建议

### 8.1 推荐主线

> 我最初假设用户愿意进入独立工具管理 AI 对话内容，但持续 dogfood 证明，捕获后的二次管理摩擦使产品无法形成闭环。因此我把系统重构为浏览器内、本地优先的记忆层。第一版词法召回随后出现大量泛词误匹配，我没有直接接入向量数据库，而是先建立候选级诊断，审计 1,493 次候选扫描，再将算法改成 precision-first gate。向量实验进一步证明了语义召回能补足换词表达，但裸余弦相似度无法满足低打扰要求，因此下一步通过真实 benchmark 验证 Hybrid Recall 和拒绝策略。

这段叙事同时覆盖产品假设、失败、数据分析、技术实现、实验设计和风险控制。

### 8.2 如何描述 AI 协作

可以坦率说明项目过程中使用 ChatGPT、Claude 和 Codex 进行研究、脑暴、代码协作和评审，但需要明确个人所有权：

> 我把多个 AI 工具作为研究与工程协作者。产品问题定义、取舍、dogfood、验收标准和最终决策由我负责；当模型给出冲突或过度设计的建议时，我通过实际数据、测试和产品原则进行判断。

面试前必须能够独立解释：

- 为什么选择 local-first；
- 为什么单词匹配不能浮现；
- 为什么相似度不是置信度；
- Anchor v2 的定位顺序和失败边界；
- MV3 写入竞态的根因与恢复路径；
- BM25、Vector、Hybrid 的差异；
- 如何设计 benchmark，避免只挑对自己有利的样本；
- 哪些 AI 建议被拒绝，以及拒绝依据。

### 8.3 不应使用的表述

避免：

- “这是一个生产级 AI 系统”；
- “向量召回准确率已经很高”；
- “项目有大量真实用户”；
- “AI 帮我完成了整个项目”；
- “相似度 0.9 代表 90% 可信”；
- “使用了 TiDB/embedding，所以有技术壁垒”。

推荐：

- “可运行并经过持续 dogfood 的本地优先 AI 应用”；
- “已有真实可靠性问题和修复证据”；
- “正在通过真实标注集建立准生产级评测”；
- “技术价值来自低打扰排序、可解释拒绝和反馈闭环，而不是单独使用向量数据库”。

## 九、面试就绪的验收标准

项目达到面试就绪，至少应具备以下材料：

- 一段 2～3 分钟的稳定演示路径；
- 一张系统架构和数据流图；
- 一份可复现的真实 Recall Benchmark；
- BM25 / Vector / Hybrid 指标对照；
- 至少三个失败案例及修复说明；
- 当前 51 个测试全部通过的验证记录；
- 一份请求级 Trace 示例；
- 一页隐私与安全边界；
- 一份方向推翻的 Case Study；
- 一份“已完成 / 未完成 / 不准备做”的诚实边界说明。

面试演示推荐顺序：

1. 在支持的 LLM 页面捕获一条想法；
2. 展示本地保存和返回原来源；
3. 在新的语境中触发相关 Echo；
4. 展示为什么某条出现、其他候选为什么被拒绝；
5. 打开 benchmark 报告，对比三种召回方案；
6. 讲述一次方向推翻和一次真实故障恢复。

## 十、最终判断

Echo 已经拥有比普通 AI Demo 更有价值的底层材料：真实产品摩擦、明确方向推翻、持续 dogfood、动态网页可靠性、浏览器运行时竞态、可解释召回和有边界的向量实验。

当前短板并不是“AI 功能太少”，而是关键结论还没有被真实数据、稳定指标和统一文档锁定。最重要的补强顺序是：

1. 真实 Recall Benchmark；
2. BM25 / Vector / Hybrid 对照；
3. 延迟、拒绝原因和失败路径 Trace；
4. 最小用户反馈事件；
5. 面试 Case Study 与安全边界。

完成前四项后，该项目可以有说服力地证明：候选人能够把模糊的 AI 产品问题转化为可运行产品，发现并修复真实失败，通过评测决定技术是否上线，并在 AI 协作开发中保持产品与工程判断。

它仍然不能证明大规模云服务、模型训练或商业化增长能力。对目标岗位而言，这种边界不需要隐藏；清楚说明哪些已经验证、哪些尚未验证，本身就是成熟工程判断的一部分。
