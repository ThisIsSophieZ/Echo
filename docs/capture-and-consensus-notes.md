# Capture And Consensus Notes

## 这份文档的定位

这不是最终规格，而是一份为了防止遗忘而写下来的产品思考笔记。

这里记录的是当前已经出现、但还没有完全定型的重要判断。后续可以基于真实使用继续修正，而不是现在就把它们写死。

## 当前核心判断

### 1. 不要过早定义“用户风格”

用户当前还不能稳定定义自己的写作风格。

原因：

- 不同文章可能需要不同风格。
- 用户真正稳定的，未必是统一风格，而可能是一些更细粒度的偏好。
- 如果系统过早学习所谓“用户风格”，很容易把局部样本误判为长期规律。

当前更合适的策略：

- 先不要急着抽象风格。
- 先积累原始片段、标注和使用轨迹。
- 让风格从长期行为中逐步浮现。

### 2. 项目优先比全局混用更重要

系统应该默认按项目组织，而不是把所有信息混在一起。

原因：

- 项目是最自然的上下文边界。
- 可以显著减少 AI 串台。
- 用户更容易理解和信任“当前项目内优先召回”的机制。

配套原则：

- 默认只检索当前项目。
- 当前项目不足时，再补充 `Global Consensus`。
- 默认不跨项目召回，除非用户主动允许。

### 3. Global Consensus 不是“风格库”

`Global Consensus` 更适合定义为“所有项目共享的高信任共识层”，而不是“系统认定的用户统一风格”。

这层更适合存放：

- 长期稳定的表达偏好
- 业务原则
- 技术红线
- 可信来源白名单
- 被反复验证的通用结论

这层暂时不适合存放：

- 仅在某一类文章中成立的风格
- 一时觉得不错的表达片段
- 还没经过反复使用验证的偏好

### 4. 冷启动阶段先做“收藏和标注”，不要急着做“共识”

当前最自然、最可信的用户动作，不是定义共识，而是：

- 这句不错，先收藏
- 这段很重要，别丢
- 这个判断以后可能用得上
- 这条内容需要复核

这非常接近用户今天已经在做的事情，例如把一段内容截到 `Obsidian`。

因此，冷启动时产品最该做的是：

- 允许低摩擦保存原始片段
- 保留来源、时间、项目和上下文
- 支持顺手写一句备注
- 后续再由系统辅助整理和升级

## 建议中的机制

### Star

最轻量的动作，只表示“这条重要”。

目标：

- 极低摩擦
- 不需要立即分类
- 保住原始上下文

### Annotation

在收藏的基础上补充一句解释。

可能的标注类型：

- 表达很好
- 这个判断靠谱
- 这段以后可复用
- 这条需要核验
- 这条只适用于某类文章

### Promotion

不是一开始就做，而是等系统积累足够观察后，再提议提升。

提升方向可以有多种：

- 提升为 `Project Memory`
- 提升为 `Global Consensus`
- 归类为某一类写作场景的风格偏好
- 继续停留在 `Scratchpad` 或候选区

## 推荐的信息分层

### Project Memory

项目内正式长期记忆。

### Global Consensus

跨项目共享的高门槛共识层。

### Candidate Inbox

系统自动采集后的候选区。

### Scratchpad

用户主动收藏、临时标注、低摩擦保存的重要片段层。

## Promotion 不应靠单次判断

当前不建议通过一次人工操作就把内容认定为“共识”。

更合理的方式是让系统观察这些信号：

- 是否跨项目反复被引用
- 是否反复被用户接受
- 是否反复被用户手动修成类似形式
- 是否来自高可信来源
- 是否属于高影响、低容错的信息
- 是否已经稳定了一段时间而没有频繁被推翻

在这些信号充分之前，系统更适合说：

- 这条内容值得继续保留
- 这条内容可能是长期偏好
- 这条内容可能值得提升为共识

而不是直接说：

- 这已经是你的长期共识

## 风格更像“条件化偏好”

当前一个重要假设是：

用户未必存在单一写作风格，而更可能存在按场景切换的偏好。

例如：

- 面向客户的写法
- 面向技术读者的写法
- 面向公开传播的写法
- 面向产品介绍的写法

所以未来更合理的方向可能不是“学习唯一风格”，而是：

- 记录用户喜欢哪些表达片段
- 识别它们分别出现在哪种上下文
- 逐渐形成“某种场景下的偏好”

## 对产品化的启发

如果未来这个产品要帮助更多人，不应该把“共识内容”做成固定模板，而应该把“共识形成机制”做成产品能力。

也就是说，产品真正要提供的是：

- 捕捉重要片段
- 保留原始证据
- 支持标注
- 观察重复模式
- 在合适时机提出提升建议

而不是替用户过早下定义。

## 真实使用时值得观察的信号

如果接下来由创始人本人先使用，可以重点观察：

- 哪些内容会被频繁收藏
- 哪些收藏后会被反复调用
- 哪些表达会在不同项目中反复复用
- 哪些条目经常被标注为“靠谱”
- 哪些内容经常需要复核，说明它们不适合进入共识层
- 哪些内容更像项目内部知识，而不是跨项目共识

## 第一轮原型验证的新洞察

在当前原型测试里，一个很明确的现象是：

- 用户愿意快速收藏重要片段
- 但不愿意在当下立刻把它提升为 `Project Memory`

这个现象更像行为设计问题，而不只是 UI 问题。

原因可能是：

- `Star` 是低负担动作，立刻带来“先别丢”的安心感
- 提升为 `Project Memory` 是正式判断动作，认知负担更高
- 收藏发生在“当下有感觉”的时刻，沉淀发生在“是否值得长期留下”的时刻，这两个时刻往往不是同一个时刻

这意味着一个重要调整：

- `Scratchpad` 不应该被理解成临时垃圾桶
- `Scratchpad` 很可能就是用户的主工作区
- `Project Memory` 更像低频沉淀层，而不是高频必做动作

因此，后续产品不应默认假设：

- 收藏之后很快就会提升

更合理的假设是：

- 用户会先大量收藏
- 之后在回看、复用、再次搜索时，才自然筛出少量值得沉淀的内容

## 对后续设计的直接影响

这条洞察会直接影响后面的交互策略：

- 不要把“提升为 `Project Memory`”设计成当前时刻的主要 CTA
- 不要让用户感觉收藏后立刻还要再做一次正式判断
- `Scratchpad` 本身必须足够好用、可搜索、可回看、可停留
- 沉淀动作更适合在回顾、整理、复用时发生

未来更合理的沉淀触发方式可能是：

- 用户主动在回看时提升
- 系统提示“这条你已经反复看过，可能值得沉淀”
- 周回顾或项目回顾时批量整理

一句简化结论：

- 收藏是高频入口
- `Scratchpad` 是主工作区
- `Project Memory` 是低频沉淀层

## 当前的产品立场

这个产品不是为“不想思考的人”设计的。

它更适合这样一类用户：

- 本来就有自己的判断
- 不愿把思考完全外包给 AI
- 希望 AI 帮自己保留、组织、验证和延长思考
- 不信任看起来很能干、但过程不透明的黑盒代理

所以它和强调全自动化的多代理产品不是同一路线。

那些产品更偏向：

- 把任务交给系统
- 让系统自己拆解和执行
- 人只负责最后批准

而这里更在意的是：

- 人持续保持判断权
- AI 不要抢走思考过程
- 系统帮助用户不遗忘、不串台、不失真

一句更清楚的话可以是：

- 这个产品不是替你思考，而是帮你保存、延长和校验思考。
- 它服务的不是不想思考的人，而是已经在认真思考的人。

## 当前阶段对人类判断的看法

当前这个阶段，人类判断仍然非常重要。

原因不是 AI 完全没用，而是：

- AI 很擅长整理和生成，但不擅长稳定承担最终判断责任
- 长上下文和项目机制很容易把人的作者性磨平成模式化语言
- 很多真正重要的内容，仍然需要人来辨别它是不是有生命力、是不是可信、是不是适合当前语境

因此，当前阶段更合理的方向不是“尽量把人移出回路”，而是：

- 让 AI 多做收集、整理、比较、提醒
- 让人保留筛选、判断、确认和定调的权力

未来如果 AI 足够强，也许这套关系会改变。

但在当前阶段，这个产品的基本判断仍然是：

- 人类辅助判断不是过渡补丁，而是核心设计原则
- 系统应该尊重人的犹豫、跳跃、反直觉和灵机一动
- 不能因为追求自动化，就把用户压平成可预测模板

## 关于作者性和灵机一动

一个重要观察是：

很多 LLM 在长上下文项目环境里，会逐渐写出“正确但无灵魂”的内容。

常见表现：

- 结构完整
- 语气稳定
- 看起来像样
- 但缺少人类思考里那种突然成立的一句、一个比喻、一次判断跃迁

这意味着系统真正应该保护的，往往不是完整答案，而是：

- 原始片段
- 临时火花
- 还没成型但很有生命感的表达
- 带有个人判断痕迹的内容

所以 `Star`、`Annotation`、`Scratchpad` 这类机制，并不是边角功能。

它们可能恰恰是在保护“人的作者性”和“人类灵机一动”的核心基础设施。

## 当前未决问题

- `Star` 和 `Scratchpad` 是同一个概念，还是前者是动作、后者是容器
- 标注是否需要固定标签体系，还是允许自然语言备注优先
- `Global Consensus` 是否需要再细分为“原则”“偏好”“已验证知识”
- 写作偏好未来应该按文章类型分类，还是按项目分类
- 何时触发“是否提升为共识”的提醒，才不会打扰用户

## 当前一句话结论

先不要试图让系统理解“我是谁”，先让系统稳定记住“我刚刚觉得什么重要”。
