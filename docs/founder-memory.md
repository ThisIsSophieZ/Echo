# Founder Memory

这份文档不是正式 PRD，而是给项目持续积累“新鲜判断、脑暴结论、未决问题和下一步假设”的工作记忆。

目标很直接：

- 防止老板脑子很好但记性不好时，重要判断在几天后丢失
- 防止我们在不同回合里重复讨论同一个问题
- 让“产品为什么往这个方向走”能够被回看，而不只剩下代码结果

更新原则：

- 每次讨论里如果出现新的产品判断、重要反直觉、设计转向或下一步假设，都应该追加到这里
- 这里记录的是“为什么”，不是逐文件改动明细
- 代码和原型层面的详细改动，另见 `docs/change-log.md`

## 2026-04-15

### 最新判断

1. 不要让 agent 直接判断“某个内容值不值得长期留下”

原因：

- 这个问题在收藏当下往往根本无法稳定判断
- 它不只是内容判断，更是时机判断和责任判断
- 如果让 agent 过早代替人做知识裁决，很容易重新滑回黑盒代理路线

当前更好的方向：

- 不让 agent 做 `judge`
- 让 agent 做 `observer + suggester`
- 它的职责不是定义“这已经是记忆”，而是提示“这条内容开始出现长期有价值的信号”

一句话版本：

- 不要让 agent 决定“什么是记忆”
- 让 agent 帮你发现“什么正在变成记忆”

### 关于沉淀的新理解

当前一个很关键的认识是：

- `沉淀` 不是收藏后的自然下一步
- `沉淀` 更像低频整理动作，而不是高频即时动作
- `Scratchpad` 很可能是主工作区
- `Project Memory` 更像低频沉淀层

这意味着：

- 不应该把 “提升为 Project Memory” 设计成默认主 CTA
- 不应该假设用户愿意在收藏后立刻做正式判断
- 更合理的触发时机，是回看、复用、整理、周回顾或被系统轻提醒的时候

### 关于标注负担的新判断

一个明确约束已经成立：

- 标注不能成为主路径

原因：

- 真实使用里，用户最愿意做的动作通常只有 `先存下来`
- 如果系统成立的前提是用户勤奋写 annotation、打标签、做结构化整理，这个系统大概率会在真实环境里失去使用频率

所以当前原则是：

- `Annotation` 保留，但必须是可选
- 系统优先依赖被动行为信号，而不是主动索取劳动

### 当前认为最值钱的被动信号

相比强迫用户持续标注，系统应该优先观察这些信号：

- 查看次数 `viewCount`
- 最近查看时间 `lastViewedAt`
- 复用次数 `reuseCount`
- 最近复用时间 `lastReusedAt`
- 最近互动时间 `lastInteractedAt`
- 收藏后过了几天仍然没有被归档

这些信号更接近真实行为，而不是理想化自我管理。

### 当前产品立场的进一步收敛

下一版的重点，不应该是：

- 让 agent 更准确地判断“该不该沉淀”

而应该是：

- 让系统更早发现“哪些内容开始反复有用”
- 让系统更自然地提示“现在是不是值得考虑沉淀”

### 已经确认的界面和交互方向

详情面板里应该出现一个更弱、更可信的判断层，而不是直接替人拍板：

- 展示 `Why this may deserve memory`
- 用信号解释，而不是用权威口吻下结论
- CTA 从“立刻提升”弱化成“加入 Project Memory”或“考虑沉淀”

### 下一步候选方向

后续优先级较高的方向：

1. 增加 `Resurface` / `Review Queue`

目标：

- 自动把“最近反复有用”的片段浮出来
- 让用户少搜一点，多被轻提醒一点

2. 继续压缩标注负担

例如：

- 默认隐藏或弱化 annotation 输入
- 只保留极少数一键动作，比如 `Mark as reused`

3. 观察真实使用而不是追求完整系统

重点不是让产品看起来更像“完整老板 OS”，而是验证：

- 几天后你会不会真的回来找这些片段
- 找回来之后它们会不会真的进入下一次写作或判断

### 当前未决问题

- `Mark as reused` 是否已经足够，还是还需要一个更轻的 “有用” 按钮
- `Resurface` 应该按什么规则排序，才能有帮助但不打扰
- 什么信号组合才适合作为“考虑沉淀”的提示阈值
- 是否要把 `Annotation` 进一步默认折叠，降低视觉负担

### 仓库管理的新判断

今天确认了一个很实际但很重要的问题：

- `solo-founder-os` 之前并不是独立仓库
- 它实际上被包含在上层 `C:\Users\Admin` 仓库里
- 这会让项目历史、状态和提交边界全部变得模糊

所以当前结论是：

- 这个项目必须拥有自己的独立 git 仓库
- 项目边界不只是产品问题，也是版本管理问题
- 如果仓库边界不清晰，后续“回看改动历史”这件事本身就会失真

一句话版本：

- 这个项目要像一个独立产品一样被版本化，而不是作为用户目录里的附属角落存在

## 2026-06-12

### 基于最新多-agent趋势的产品收敛判断

在重新看最近论文、协议和社区讨论后，一个判断明显变强了：

- 这个项目下一阶段不应该追求“做出一个多-agent系统”
- 更应该追求“做出一个有状态、可回放、可审计的 founder workflow system”

原因不是我们保守，而是最近行业里真正跑出来的方向，本身就在收敛到：

- 更少但更明确的 agent 角色
- 更强的 orchestration，而不是更热闹的 agent 群聊
- 更重视 memory、state、trace、permission 和 rollback
- 更重视垂直工作流里的真实帮助，而不是通用自治感

一句话版本：

- 趋势不是 `more agents`
- 趋势是 `better state machines for human-supervised work`

### 当前项目应该明确保留的东西

1. 保留 `human in the loop` 作为核心立场

这不只是价值观问题，也越来越符合真实工程趋势：

- 高价值任务里，大家更在意可控、可追责、可撤回
- 完全自治 agent 在 demo 里很亮眼，但在长期工作流里不稳定

2. 保留 `observer + suggester`，不要回到 `judge + decider`

尤其在“值不值得沉淀”这个问题上：

- 行业趋势并没有证明 agent 已经足够可靠到能替人做长期知识裁决
- 你的原型现在这条路反而更对：先观察信号，再提示人

3. 保留 `状态分层`

目前仓库里最值钱的产品结构，仍然是：

- `Scratchpad / fragments`
- `Project Memory`
- 人工确认后的正式沉淀

这套分层很像把“思考过程”和“正式知识”区分开，方向是对的。

4. 保留 `证据和来源意识`

后面不管是否上多 agent，系统都应该继续坚持：

- 记忆
- 外部事实
- 模型推断

这三类内容分开显示、分开追溯。

### 当前项目应该主动砍掉或降级的东西

1. 砍掉“多-agent协作”作为近期产品主叙事

至少当前阶段，不应该把产品讲成：

- 一个会自己分工、自己讨论、自己沉淀的 agent team

因为这会把注意力从真正难的点上带偏：

- 状态是否可靠
- 提示是否有帮助
- 记忆是否真的会被再次使用

更合适的叙事是：

- 一个帮 founder 保存上下文、 resurfacing 线索、辅助判断的工作台

2. 降级“自动沉淀”期待

下一阶段不该继续追求：

- 让系统更聪明地自动决定该不该进 `Project Memory`

应该改成：

- 让系统更自然地把“可能值得复查的东西”重新浮出来

3. 暂时不要做“很多 agent 角色”

例如：

- researcher
- writer
- critic
- memory curator
- planner

这种多角色编排现在对这个项目来说大概率是复杂度先于价值。

当前更合理的是：

- 最多一个 `orchestrator`
- 再加一个非常具体的辅助角色，比如 `verifier` 或 `research helper`

### 当前项目应该延后的东西

1. 延后正式的 agent-to-agent 协议层

像 A2A、复杂 delegation、跨 agent 会话这些方向值得关注，但不应该先做。

这类能力更适合在下面这些条件成立后再考虑：

- 单 agent 工作流已经稳定
- 状态与审计足够清晰
- 真实任务里确实出现了明确的拆工需求

2. 延后 `Global Consensus` 的重投入实现

它在概念上是对的，但现在更像二级问题。

在 `Project Memory` 还没有稳定复用之前，太早做全局共识层，容易让系统结构比真实使用更复杂。

3. 延后“自主长期运行”

最近趋势虽然在谈 agent teams，但真正落地成功的案例通常也都限定在：

- 明确边界
- 明确权限
- 明确回滚

所以不要太早做后台长期自治循环，先把短链路任务打通。

### 现在更值得押注的新方向

1. `Resurface / Review Queue` 应该上升为下一阶段主线

如果趋势在告诉我们“stateful workflow 比 swarm 更重要”，那这个项目最该做的不是更多 agent，而是：

- 把过几天后仍然可能有价值的片段重新浮出来
- 给出简短解释：为什么浮出来
- 让用户一键决定：忽略、稍后再看、加入 memory

2. 把 `memory` 从“对象”继续推进成“过程”

也就是说，系统要记录的不只是：

- 这条内容在不在 `Project Memory`

还要记录：

- 它什么时候被再次看到
- 什么时候被复用
- 什么时候被正式确认
- 什么时候又变 stale

这比“是否沉淀”的单点判断更符合真实工作。

3. 如果要加第二个 agent，优先加 `Verifier`

不是加“更聪明的 curator”，而是加一个边界更清楚的能力：

- 检查来源
- 对比说法
- 标出不一致
- 给出证据链接

这比让多个 agent 讨论“值不值得记住”更有现实价值。

### 对这个项目的新一句话定位

比起：

- `multi-agent OS for solo founders`

当前更适合的定位可能是：

- `a stateful evidence-and-memory workspace for solo founders`

或者更口语一点：

- 不是替 founder 思考的一群 agent
- 而是一个能记住过程、重新浮现线索、辅助判断的工作台

### 当前最建议的实现顺序

1. 先修当前 prototype 和 backend 的状态断裂问题

包括之前已经发现的：

- 新建 project 不持久化
- promote to memory 不持久化
- 行为信号时间戳不持久化

2. 再做 `Resurface / Review Queue`

这是最接近新产品判断、也最能验证真实价值的一步。

3. 然后补一层 `why surfaced` / `why worth review`

让系统解释为什么把一条内容重新推到面前。

4. 最后才考虑是否需要第二个 agent 角色

而且前提是：

- 单条工作流已经能持续产生帮助

### 当前未决问题

- `Resurface` 的最小触发规则应该是什么，才能既有帮助又不打扰
- `Project Memory` 是否应该显式增加 `stale` 或 `needs revalidation` 状态
- `Verifier` 是先做成按钮式能力，还是做成自动陪跑的轻检查
- 现在要不要先把产品叙事从“agent”改成“workflow + memory + evidence”

## 2026-06-17

### 新判断：从 Founder OS 收敛到 ChatGPT Collect 原型

今天的讨论把项目方向进一步压实了。

之前一直说 `Solo Founder OS`，但它包含的东西太多：

- 长期记忆
- 写作辅助
- 事实核验
- 多 agent
- 项目工作台
- 全局共识
- 资料库

这些灵感仍然重要，不应该删掉。

但当前真正最痛、最清楚、最适合先做原型的问题是：

- 用户记忆力差
- 前学后忘
- AI 对话里经常出现当时觉得非常有用的点
- 这些点过几天很容易找不回来
- 传统笔记和知识库都假设用户会整理、搜索、回看
- 实际上，用户经常连“自己应该去找什么”都忘了

所以当前项目可以从一个更小的入口开始：

> 在 ChatGPT 网页中选中一段 useful point，点 `Collect` 保存；之后系统和后台 agent 负责整理、找回、重新浮现。

### 这不是删除旧方向，而是更新入口

原来的 `Solo Founder OS` 仍然是上层愿景。

当前更新后的关系是：

- `ChatGPT Collect` 是第一阶段入口实验
- `Project Memory` 仍然是沉淀层
- `Resurface / Review Queue` 仍然是核心价值
- `Global Consensus` 仍然是后续高门槛共识层
- `Verification Desk` 仍然可以在以后处理事实和时效性
- agent 仍然存在，但角色从“多 agent 系统”收敛为“后台碎片整理员”

一句话：

- 不是推翻之前的灵感
- 而是先把最窄、最痛、最容易自用的入口做出来

### 关于“像不像印象笔记”的判断

这个方向确实像“AI 时代的 Web Clipper”。

但它不能变成普通备忘录或普通知识库。

普通备忘录的问题是：

- 保存就是结束
- 用户要自己整理
- 用户要自己搜索
- 很容易变成数字灰尘

这个项目的不同点应该是：

- 保存只是开始
- 核心对象不是普通 note，而是 AI 对话里的 useful point
- 系统要让旧想法重新回来
- 后台 agent 要降低整理负担
- 反复出现、反复有用的内容才逐步进入正式记忆

当前内部原则：

> 不要做一个更漂亮的备忘录，要做一个让旧想法回来找用户的工具。

### agent 的新定位

agent 不是用来替用户最终判断，而是用来在后台整理碎片。

第一版 agent 可以做：

- 给碎片补短标题
- 提取主题标签
- 找出相似片段
- 生成轻摘要
- 发现反复出现的想法
- 生成 `Review Queue`
- 给出 `why surfaced`

agent 不应该做：

- 自动删除碎片
- 自动合并正式记忆
- 自动决定什么一定重要
- 自动把内容提升到 `Project Memory`

更合适的链路是：

`Collect -> agent enriches -> resurface -> human confirms -> memory`

### 当前最建议的下一步

为了加快进度，不继续抽象讨论完整 OS。

下一步直接做一个自己能用的原型：

1. 修现有本地 API 和 prototype 的持久化断裂
2. 新增 ChatGPT 网页选中 `Collect` 入口
3. 保存内容、项目、来源 URL、来源标题、时间、可选 note
4. 在本地 review 页面看到这些 collected points
5. 加 `Useful Again`
6. 再做最小 `Review Queue`

### 当前验证标准

这个方向是否成立，不看功能是不是完整，而看：

- 用户是否真的频繁 collect
- 几天后是否真的找回旧片段
- 旧片段是否被再次用于写作、产品判断或技术理解
- agent 是否减少了整理负担
- 系统是否让用户感觉“重要想法有第二次出现的机会”
