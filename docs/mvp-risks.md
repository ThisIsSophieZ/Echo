# MVP Risks

## 文档定位

这份文档记录 `ChatGPT Collect / Memory Layer` 当前 MVP 的主要风险。

当前判断：

- 方向合理
- 右键收藏链路已经跑通
- 下一步重点不再是继续扩展捕获入口，而是验证 `Review Queue / Resurface` 是否真的让旧片段被重新使用

一句话：

> 当前最危险的不是做不出来，而是做成一个更顺手的备忘录，却没有证明旧想法会回来。

---

## 1. Review Queue 仍然需要用户主动打开

### 风险

`Review Queue` 比手动搜索轻，但仍然要求用户主动进入 review 页面。

如果用户几天后根本不打开 review 页面，那么它仍然会滑回普通知识库：

- 收藏成功
- 数据进入库
- 用户忘了回来
- 片段继续沉底

这和项目最初想解决的问题是同一个问题：用户经常连“自己该去找什么”都忘了。

### 为什么重要

当前产品的核心价值不是 `store`，而是 `return`。

如果旧片段不能重新回到用户工作流中，`Memory Layer` 就会退化成：

- 右键收藏器
- 本地资料库
- 更私人的印象笔记

### MVP 应对

Phase 0 仍然可以先做 app 内 `Review Queue`，但要把验证标准写得更硬：

- 用户是否愿意持续打开 review 页面
- 每次打开是否真的点击旧片段
- 是否至少有几条片段被重新用于写作、产品判断或技术理解

### 后续观察

如果 review 页面打开频率低，就不要立刻加 embedding 或 agent。

应优先考虑：

- 更明显的首页入口
- 启动本地服务后自动打开 review 页面
- 每日轻提醒
- 浏览器扩展 popup 里展示 1-3 条今日浮现
- Phase 2 的 ChatGPT 页内语境浮现

## 2. Project Memory 边界可能变模糊

### 风险

`memory-layer-design.md` 提到：

> 不再依赖手动 promote。`Project Memory` 不是“你搬上去”的，而是“沉淀出来”的。

这个方向是对的，因为手动 promote 太重。

但需要小心：行为信号可以让内容升温，却不应该自动把内容变成正式记忆。

否则 `Project Memory` 可能被这些内容污染：

- 看过很多次但只是因为困惑
- 被频繁浮现但没有真实价值
- 只是最近活跃，不代表长期重要
- 来源不可靠但互动很多

### 为什么重要

`Scratchpad` 和 `Project Memory` 的分层，是当前产品最重要的结构之一。

如果正式记忆层失去门槛，后面写作台、验证台和全局共识都会被污染。

### MVP 应对

建议区分两个概念：

- `warmth`：机器根据行为信号计算出来的热度
- `memory`：用户明确确认过的正式记忆

机器可以做：

- 升温
- 排序
- 推荐沉淀
- 解释为什么值得复看

机器不应该在 MVP 做：

- 自动提升到 `Project Memory`
- 自动合并正式记忆
- 自动删除或覆盖旧记忆

### 推荐原则

> 升温可以自动，正式沉淀仍然需要人点确认。

## 3. 本地向量可能过早

### 风险

本地 embedding 是合理方向，但不一定应该进入最小 MVP。

它会引入额外复杂度：

- 首次下载模型
- Python 依赖
- 向量字段迁移
- 计算耗时
- 相似度阈值调参
- 中英混合模型选择
- 用户很难判断“为什么相似”

如果太早引入，本来要验证的核心问题会被技术实现分散。

### 为什么重要

当前已经跑通了右键收藏。

下一步最需要验证的是：

- 用户是否会持续收藏
- 旧片段浮现后是否会被点击或复用
- `why surfaced` 是否有帮助

这些问题用关键词和行为信号已经可以开始验证。

### MVP 应对

Phase 0 建议只用零依赖规则：

- 收藏时间
- 是否有备注
- 是否被复用
- 是否很久没看
- 是否最近被查看
- sourceType 是否为 `chatgpt`
- 简单关键词重叠

当真实数据达到几十到几百条，并且出现明显问题时，再上 embedding：

- 关键词召回太弱
- 同义表达找不到
- review queue 质量明显不够

### 推荐原则

> 先证明“浮现有用”，再优化“相关性更准”。

## 4. “别人没做”这个判断需要更谨慎

### 风险

PRD 里提到：

> 市面上“收藏 + 存库”工具很多，但几乎没人做“被动的、上下文相关的二次浮现”。

这个判断方向可以保留，但表述需要谨慎。

相邻产品其实存在：

- Readwise 有复习和 resurfacing
- Recall 有知识库连接和 browsing 时的相关内容浮现
- Mem / mymind 等也碰过自动关联和找回

所以风险不是“完全没人做”，而是我们可能高估差异点的新颖性。

### 更稳的判断

真正更具体的差异应该是：

> 很少有产品把 resurfacing 做成 AI 对话工作流里的反遗忘层。

也就是说，差异点不是泛泛的 `resurface`，而是组合：

- 输入源是 AI 对话里的 useful point
- 收藏动作极轻
- 数据本地
- 按项目组织
- 后续在工作语境里重新浮现
- 人最终判断，机器只做连接和提示

### MVP 应对

短期不需要做完整竞品分析。

但在产品文案里应避免绝对化表达：

- 不说“没人做”
- 改成“很少有人贴着 AI 对话工作流做”
- 强调自用痛点和具体 workflow，而不是抽象赛道

## 5. 本地服务与扩展安装摩擦较高

### 风险

当前架构是：

- Chrome extension
- 本地 FastAPI
- SQLite
- 手动 load unpacked
- review 页面

对自用原型是合理的。

但如果以后给别人用，门槛会明显偏高：

- 需要启动本地服务
- 需要手动安装扩展
- 需要理解本地端口
- Chrome 137+ 不再支持普通命令行 `--load-extension`
- 服务没启动时右键菜单需要刷新

### 为什么重要

MVP 阶段不要过早商业化，但也要意识到：

> 自用可行，不等于分发可行。

这个风险不影响当前方向，但会影响后续产品化路线。

### MVP 应对

当前阶段接受这个摩擦，把目标限定为自己连续使用。

暂时不做：

- 云同步
- 一键安装包
- 多浏览器适配
- 账号系统
- 多设备

等自用链路成立后，再评估是否需要：

- 桌面 app 包装本地服务
- 扩展自动检测服务状态
- popup 内展示启动提示
- 数据导出 / 备份

## 6. 容易重新滑向“带 AI 的备忘录”

### 风险

如果后续只继续加强这些能力：

- 更方便收藏
- 更多字段
- 更好搜索
- 更复杂标签
- 更漂亮列表

但没有强化 `return`，产品就会变成：

- 本地印象笔记
- AI 对话收藏夹
- 碎片仓库

这不一定没用，但不是当前项目最有价值的方向。

### 判断标准

它是不是备忘录，不看有没有收藏功能，而看：

- 旧片段是否主动回来
- 回来时是否解释原因
- 用户是否真的复用
- 系统是否因为复用而改变后续排序

### MVP 应对

接下来优先级应是：

1. `Review Queue`
2. `why surfaced`
3. `Useful Again`
4. `snoozeUntil`
5. `lastSurfacedAt`

而不是：

- 更多入口
- 更多整理字段
- 更复杂分类
- 更智能 agent

---

## 7. MVP 推荐边界

### 当前已经完成

- ChatGPT 选中文字
- 右键收藏到项目
- 本地 SQLite 持久化
- prototype review 页面可见

### 下一步只做

- App 内 `Review Queue`
- 每次 3-5 条
- 每条一句 `why surfaced`
- `Useful Again`
- `Snooze`
- `Archive`
- `Promote`
- 写入 `lastSurfacedAt`
- 写入 `snoozeUntil`

### 暂时不要做

- embedding
- 后台整理 agent
- ChatGPT 页内实时提醒
- 自动沉淀
- 自动合并
- 多入口支持
- 云同步

### 通过标准

自用 1-2 周后，如果出现下面信号，就说明方向值得继续：

- 每周至少多次主动打开 review 页面
- review queue 中的片段被点击
- 至少几条片段被标记 `Useful Again`
- 至少几条片段进入写作、产品判断或技术理解
- 浮现频率没有造成明显打扰

如果没有这些信号，应优先调整浮现入口和时机，而不是继续加模型能力。
