# Change Log

这份文档记录每次实际改动了什么、为什么改、改动范围、验证方式和后续观察点。

目标：

- 防止几天后忘记“我们到底已经改过什么”
- 让每次原型迭代都能回溯到明确的动机和结果
- 区分“产品判断”与“实际实现”

记录原则：

- 每次有代码、原型、文档层面的实际变更，都应该追加一条记录
- 每条记录尽量回答：
  - 为什么要改
  - 具体改了什么
  - 影响了哪些文件
  - 做了哪些验证
  - 下一步该观察什么

## 2026-04-15

### 变更 001：Prototype v0.2 从“沉淀判断”切到“行为信号”

#### 背景

在连续使用原型几天后，一个核心矛盾变得更明显：

- “某个内容值不值得长期留下”这个问题太难在收藏当下稳定判断
- 如果要求用户频繁写标注、做判断，真实使用很容易变懒
- 如果让 agent 直接判断，又会偏离产品当前强调的 `human in the loop`

因此，这次升级的目标不是让系统直接决定是否沉淀，而是：

- 让系统记录更真实的行为信号
- 让系统展示“为什么它可能值得沉淀”
- 减少用户显式标注负担

#### 具体改动

1. 给片段和正式记忆增加了行为信号字段

新增字段：

- `viewCount`
- `lastViewedAt`
- `reuseCount`
- `lastReusedAt`
- `lastInteractedAt`

作用：

- 让系统能根据实际使用轨迹，而不是主观表单输入，推断一条内容是否开始变得长期有价值

2. 详情选择动作会自动记录查看行为

现在当用户点开一条 `fragment` 或 `memory` 时，系统会自动记录：

- 查看次数增加
- 最近查看时间更新
- 最近互动时间更新

这使得“回看”本身就成为信号，不需要额外点很多按钮。

3. 新增超轻动作 `Mark as reused`

设计意图：

- 用户不必写长备注
- 只要在真实复用时点一次，就能给系统一个高价值信号

这比强迫持续 annotation 更贴近真实工作流。

4. 详情面板新增 `Why this may deserve memory`

这个面板不直接替人拍板，而是解释信号，例如：

- 已查看多次
- 已复用
- 收藏后跨了几天仍未归档
- 留过备注
- 不是收藏当下看一眼就结束，而是后续又回来确认过

状态文案分为：

- `继续观察`
- `可以考虑沉淀`
- `已沉淀`

5. 调整了文案，降低“立刻沉淀”的压力

包括：

- `Quick Capture` 区明确写出 Annotation 是可选的
- 侧栏说明从“补一句 Annotation”改成“尽量少标注，多看行为信号”
- 详情区 CTA 从“提升为 Project Memory”弱化成“加入 Project Memory”
- 详情提示文案改成“先保留，等反复查看/复用/跨时间仍然有用后再考虑沉淀”

6. 列表卡片增加行为信号提示

现在每条卡片会显示：

- 看过几次
- 复用几次
- 最近查看 / 最近复用

这样用户不必点进详情也能快速感知这条内容是否“活着”。

7. 加入旧数据兼容和迁移

为了不破坏此前已经保存在 `localStorage` 的原型数据，加载时会自动补齐新字段默认值。

这意味着旧版本数据可以直接继续用，不需要手工清空。

#### 影响文件

- `prototype/index.html`
- `prototype/app.js`
- `prototype/styles.css`

#### 验证

已完成：

- 使用 `node --check prototype/app.js` 进行语法检查，结果通过
- 检查新 DOM 节点与 JS 引用是否一一对应，结果正常

未完成：

- 还没有在真实浏览器中手工完整点测一轮交互

#### 这次改动想验证什么

不是验证：

- agent 能不能替人判断“该不该沉淀”

而是验证：

- 被动行为信号能不能比显式标注更自然地积累价值判断
- 用户会不会真的做 `回看` 和 `Mark as reused`
- `Why this may deserve memory` 这种提示方式是否比“直接建议沉淀”更可信

#### 下一步观察点

- 你会不会比以前更频繁地点开旧片段
- `Mark as reused` 是否会自然发生，还是仍然嫌多一步
- 是否需要增加一个更主动但不打扰的 `Resurface / Review Queue`
- 是否应该进一步弱化或折叠 `Annotation`

### 变更 003：将 `solo-founder-os` 收为独立 git 仓库

#### 背景

今天确认了一个仓库边界问题：

- `solo-founder-os` 虽然有过提交记录
- 但这些提交实际上属于上层仓库 `C:\Users\Admin`
- 这导致当前项目的 git 状态会混入整个用户目录，不适合作为独立项目继续开发

这个问题如果不修，后面会持续影响：

- 提交边界
- 历史回看
- 版本控制可信度
- 对项目本身的所有权感

#### 具体改动

1. 为 `C:\Users\Admin\solo-founder-os` 初始化独立 git 仓库

目标：

- 让项目拥有自己的 `.git`
- 让后续提交、分支、状态都只围绕这个项目本身

2. 将当前项目内容作为独立仓库的第一笔正式提交

包含：

- 产品定义文档
- 原型文件
- 持续记忆文档
- 当前已实现的行为信号版原型

3. 把这次仓库边界修正记录进持续文档

避免几天后再次忘记：

- 为什么要单独建仓库
- 之前的问题到底是什么

#### 影响文件

- `docs/founder-memory.md`
- `docs/change-log.md`
- `.git/`（项目独立仓库元数据）

#### 验证

已完成：

- `solo-founder-os` 目录内出现独立 `.git`
- 在项目目录内运行 `git status` 只显示项目自己的状态
- 第一笔独立提交成功创建

#### 这次改动想解决什么

- 让项目的版本历史和产品边界重新对齐
- 避免整个用户目录污染当前项目的 git 视图
- 给后续每次提交提供可信的独立历史起点

### 变更 004：接入 GitHub remote 并推送独立仓库

#### 背景

在项目完成独立 git 初始化之后，下一步需要把这份历史推到真正的远程仓库里。

如果只停留在本地：

- 历史仍然容易丢失
- 版本回看和备份都不够稳
- 项目虽然形式上独立了，但还没有真正进入可协作、可恢复、可追踪的状态

#### 具体改动

1. 为独立仓库添加 `origin`

目标：

- 把本地仓库和 GitHub 仓库 `ThisIsSophieZ/solo-founder-os` 对齐

2. 提交本次文档更新

包含：

- 记录仓库独立化
- 记录接入 remote 与推送这件事本身

3. 将 `main` 推送到 GitHub

目标：

- 让这个项目拥有真正独立、可回看的远程历史起点

#### 影响文件

- `docs/change-log.md`
- git remote 配置
- GitHub 远程仓库中的 `main`

#### 验证

计划验证：

- `git remote -v` 中出现 `origin`
- `git push -u origin main` 成功
- GitHub 远程仓库可看到首批提交历史

#### 这次改动想解决什么

- 给项目加上远程备份
- 让本地独立仓库真正落地为独立项目
- 避免之后再次出现“项目明明存在，但历史散落在错误地方”的情况

### 变更 005：基于最新多-agent趋势，收敛下一阶段产品重点

#### 背景

在项目停了一段时间之后，重新审视“下一步该往哪里做”比继续加功能更重要。

这次专门结合了最近的：

- 多-agent论文
- 新协议方向
- 社区与工程讨论

再回看当前项目原型和之前已经暴露的问题，得到一个更清晰的结论：

- 下一阶段不该继续往“更多 agent、更强自治”推进
- 而应该把重点收敛到 `state + memory + evidence + review workflow`

#### 具体改动

1. 在 `docs/founder-memory.md` 中追加新的战略判断

新增内容主要回答：

- 什么应该继续保留
- 什么应该主动砍掉或降级

- 下一阶段最值得押注的实现顺序是什么

原因：

- 它更符合最近行业里“少 agent、强 orchestration、强状态”的实际趋势
- 也更贴近当前原型真正想验证的问题：哪些内容会在几天后再次变得有用

3. 明确把“多-agent协作”从近期主叙事中降级

不是否认它有价值，而是确认：

- 对这个项目来说，当前真正缺的不是更多 agent 身份
- 而是更可靠的状态流转、解释层和复查工作流

#### 影响文件

- `docs/founder-memory.md`
- `docs/change-log.md`

#### 验证

已完成：

- 重新对齐当前仓库状态、原型方向和前一轮 review 发现的问题
- 将本轮新的产品判断落入长期文档，避免再次只停留在聊天里

未完成：

- 还没有把这轮战略收敛进一步翻译成新的 roadmap 或实际代码改动

#### 这次改动想解决什么

- 防止项目继续在“要不要更多 agent”上消耗注意力
- 给下一步重构提供更清晰的取舍标准

#### 下一步观察点

## 2026-06-17

### 变更 006：新增 `ChatGPT Collect` 原型项目，保留并更新旧愿景

#### 背景

继续讨论后，一个更具体的个人痛点浮出来：

- 用户记忆力差
- 前学后忘
- AI 对话里有很多当时很有用的判断和句子
- 这些内容如果不当场保存，之后很难重新找回
- 普通知识库、备忘录、收藏夹都太依赖用户主动整理和搜索

因此，当前最适合加快进度的方向不是继续扩展完整 `Solo Founder OS`，而是先做一个可以自用的极窄入口：

`在 ChatGPT 网页选中一段 useful point -> 点击 Collect -> 保存到本地项目库 -> 后台整理 -> 后续重新浮现`

#### 具体改动

1. 新增 `docs/chatgpt-collect-project.md`

这份文档把新原型项目写成独立需求说明，包括：

- 前因后果
- 和旧 `Solo Founder OS` 愿景的关系
- MVP 范围
- 保存字段
- ChatGPT 网页选中收藏流程
- 后台整理 agent 的边界
- `Review Queue` 和后续实时 resurfacing
- 第一版不做什么
- 下一步实现顺序

2. 更新 `README.md`

把仓库状态从早期 `docs-first` 更新为本地原型阶段，并新增当前执行方向：

- `ChatGPT Collect` 是当前优先项目
- 旧的 `Solo Founder OS` 愿景保留
- 当前先验证反遗忘入口
- agent 先作为后台整理员

3. 更新 `docs/roadmap.md`

在原 roadmap 前面追加 `2026-06-17 当前执行项目`。

没有删除原来的阶段规划，而是把它们保留为更长期的路线。

4. 更新 `docs/founder-memory.md`

追加这次产品判断：

- 不是推翻旧方向，而是更新入口
- 当前最痛的问题是 `AI 对话 useful point` 的丢失
- 产品不应变成普通备忘录
- agent 的合适位置是后台整理碎片
